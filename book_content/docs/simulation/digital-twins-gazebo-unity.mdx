# Digital Twins with Gazebo and Unity

## Learning outcomes

- Explain why simulation is required before physical robot deployment.
- Compare Gazebo physics simulation and Unity visualization roles.
- Identify how URDF, SDF, LiDAR, depth cameras, and IMUs support robot testing.
- Design a simulation test for a humanoid task.
- Construct URDF and SDF files that define robot kinematics, dynamics, and sensor placement.
- Configure sensor plugins with realistic noise models, update rates, and field-of-view constraints.
- Analyze physics engine tradeoffs between ODE, Bullet, DART, and MuJoCo for different robot morphologies.
- Apply domain randomization and sim-to-real transfer techniques to reduce the reality gap.
- Debug common simulation pitfalls including interpenetration, floating-base instability, and sensor aliasing.

## Concept explanation

### Why simulation before hardware

A digital twin is a simulated version of a robot, environment, or interaction. It is not a perfect copy of reality. It is a controlled test space where learners can expose problems before a machine moves in the real world. Simulation provides three critical advantages over immediate hardware deployment:

1. **Safety** -- You can test failure modes (joint over-torque, unstable gaits, collision recovery) without destroying hardware or injuring people.
2. **Repeatability** -- Every run starts from identical initial conditions, enabling controlled experiments that isolate single variables.
3. **Speed** -- Hundreds of test episodes can run in parallel on a compute cluster, compressing months of physical testing into hours.

### Gazebo: the physics-first simulator

Gazebo is useful for physics, collisions, gravity, robot descriptions, and sensor simulation. It was designed specifically for robotics research and integrates natively with ROS and ROS 2 through dedicated bridge packages. Gazebo uses plugin-based architecture: every sensor, physics engine, and middleware integration is a loadable plugin. This makes it extensible but also means configuration is often verbose.

Key Gazebo capabilities for humanoid simulation:

- **Physics engines**: ODE (default), Bullet, DART, and Simbody can be selected per-world.
- **Sensor plugins**: Camera, depth camera, LiDAR (ray and GPU), IMU, force-torque,接触传感器, GPS, and magnetometer plugins ship with standard Gazebo distributions.
- **Model database**: A community-maintained model repository provides pre-built robots, objects, and environments.
- **ROS integration**: `gazebo_ros_pkgs` and the newer `ros_gz` bridge provide bidirectional topic and service communication between Gazebo and ROS 2 nodes.

### Unity: high-fidelity visualization and interaction

Unity can provide high-fidelity visualization and human-robot interaction scenes. It is built on a real-time rendering engine originally designed for games, which gives it advantages in visual quality, animation, and VR/AR integration. However, Unity was not designed for robotics, so physics and ROS integration require careful setup.

Key Unity capabilities for humanoid simulation:

- **URDF Importer**: Unity Robotics package parses URDF files and creates articulated robot GameObjects with joint controllers.
- **ROS TCP Connector**: A network-based bridge that streams ROS 2 topics (sensor data, joint states, commands) between Unity and a ROS 2 workspace over TCP.
- **ML-Agents**: Reinforcement learning toolkit that allows training policies directly in Unity environments.
- **HDRP rendering**: High Definition Render Pipeline produces photorealistic scenes useful for training vision-based algorithms.

### Isaac Sim: NVIDIA's simulation platform

Isaac Sim provides photorealistic robotics simulation and synthetic data generation built on NVIDIA Omniverse. It uses RTX ray tracing for physically accurate lighting and reflections. It requires RTX hardware or a suitable cloud GPU. Isaac Sim is particularly strong for:

- Synthetic data generation for training perception models.
- Large-scale parallel simulation with GPU-accelerated physics.
- Integration with NVIDIA's robotics stack (Isaac Lab, Isaac Cortex).

Together these three tools help students understand both the mechanics and the experience of robotics.

### Key URDF elements explained

| Element | Purpose |
|---|---|
| `<link>` | A rigid body in the kinematic chain with visual, collision, and inertial properties |
| `<joint>` | Connects two links with type (revolute, prismatic, fixed, continuous), axis, limits, and dynamics |
| `<visual>` | Defines appearance (mesh or primitive geometry) used for rendering |
| `<collision>` | Defines geometry used by the physics engine for contact detection |
| `<inertial>` | Mass and 3x3 inertia tensor used by the dynamics engine |
| `<gazebo>` | Gazebo-specific extensions for sensor plugins, material colors, and references |

## SDF world file example

SDF (Simulation Description Format) is more expressive than URDF and is the native format for Gazebo worlds. A world file defines the simulation environment including gravity, physics engine, lighting, models, and sensor configurations.

```xml

  <world name="humanoid_test_world">

    <!-- Physics engine configuration -->
    <physics name="ode_physics" type="ode">
      <max_step_size>0.001</max_step_size>
      <real_time_factor>1.0</real_time_factor>
      <real_time_update_rate>1000</real_time_update_rate>
      <ode>
        <solver>
          <type>dantzig</type>
          <iters>50</iters>
          <sor>1.3</sor>
        </solver>
        <constraints>
          <cfm>0.0</cfm>
          <erp>0.2</erp>
          <contact_max_correcting_vel>100.0</contact_max_correcting_vel>
          <contact_surface_layer>0.001</contact_surface_layer>
        </constraints>
      </ode>
    </physics>

    <!-- Gravity -->
    <gravity>0 0 -9.81</gravity>

    <!-- Magnetic field (for IMU simulation) -->
    <magnetic_field>5.6e-06 1.68e-05 -4.94e-05</magnetic_field>
```

## Spawning robots in Gazebo with Python

The following Python script spawns a robot model into a running Gazebo instance using the Gazebo ROS service interface:

```python
import rclpy
from rclpy.node import Node
from gazebo_msgs.srv import SpawnEntity
import os
import xacro


class RobotSpawner(Node):
    def __init__(self):
        super().__init__('robot_spawner')
        self.client = self.create_client(SpawnEntity, '/spawn_entity')
        while not self.client.wait_for_service(timeout_sec=1.0):
            self.get_logger().info('Waiting for /spawn_entity service...')

    def spawn_from_xacro(self, xacro_path, robot_name, namespace=''):
        doc = xacro.process_file(xacro_path)
        robot_description = doc.toxml()

        request = SpawnEntity.Request()
        request.name = robot_name
        request.xml = robot_description
        request.robot_namespace = namespace
        request.reference_frame = 'world'

        future = self.client.call_async(request)
        rclpy.spin_until_future_complete(self, future)

        if future.result() is not None:
            self.get_logger().info(
                f'Spawned {robot_name}: {future.result().status_message}'
            )
        else:
            self.get_logger().error(
                f'Failed to spawn {robot_name}: {future.exception()}'
            )


def main():
    rclpy.init()
    spawner = RobotSpawner()

    xacro_file = os.path.join(
        os.getcwd(),
        'src', 'my_robot', 'urdf', 'humanoid.urdf.xacro'
    )
    spawner.spawn_from_xacro(xacro_file, 'minimal_humanoid', '/robot')

    spawner.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()
```

## ROS 2 launch file for Gazebo simulation

A launch file orchestrates the startup of Gazebo, the robot state publisher, and controller nodes:

```python
import os
from ament_index_python.packages import get_package_share_directory
from launch import LaunchDescription
from launch.actions import ExecuteProcess, IncludeLaunchDescription
from launch.launch_description_sources import PythonLaunchDescriptionSource
from launch_ros.actions import Node


def generate_launch_description():
    pkg_share = get_package_share_directory('my_robot_description')
    gazebo_share = get_package_share_directory('gazebo_ros')
    world_file = os.path.join(pkg_share, 'worlds', 'humanoid_test_world.sdf')
    urdf_file = os.path.join(pkg_share, 'urdf', 'humanoid.urdf')

    with open(urdf_file, 'r') as f:
        robot_description = f.read()

    # Launch Gazebo with the custom world
    gazebo = IncludeLaunchDescription(
        PythonLaunchDescriptionSource(
            os.path.join(gazebo_share, 'launch', 'gazebo.launch.py')
        ),
        launch_arguments={'world': world_file}.items(),
    )

    # Robot state publisher publishes TF transforms from URDF
    robot_state_publisher = Node(
        package='robot_state_publisher',
        executable='robot_state_publisher',
        parameters=[{'robot_description': robot_description}],
        output='screen',
    )

    # Joint state publisher for simulating joint values
    joint_state_publisher = Node(
        package='joint_state_publisher',
        executable='joint_state_publisher',
        name='joint_state_publisher',
        parameters=[{'use_sim_time': True}],
    )

    # Spawn the robot entity in Gazebo
    spawn_entity = Node(
        package='gazebo_ros',
        executable='spawn_entity.py',
        arguments=[
            '-topic', 'robot_description',
            '-entity', 'minimal_humanoid',
            '-z', '1.2',
        ],
        output='screen',
    )

    return LaunchDescription([
        gazebo,
        robot_state_publisher,
        joint_state_publisher,
        spawn_entity,
    ])
```

## Unity ROS TCP connector setup

The ROS TCP Connector enables bidirectional communication between Unity and a ROS 2 workspace. Setup requires both a Unity-side package and a ROS-side endpoint node.

### Unity-side setup (C# component)

```csharp
using Unity.Robotics.ROSTCPConnector;
using UnityEngine;

public class ROSBridgeSetup : MonoBehaviour
{
    [SerializeField] string rosIPAddress = "127.0.0.1";
    [SerializeField] int rosPort = 10000;

    void Awake()
    {
        ROSConnection.instance.Connect(
            rosIPAddress,
            rosPort
        );
    }

    void Start()
    {
        // Subscribe to a ROS 2 topic
        ROSConnection.instance.Subscribe<GeometryMsgsTwist>(
            "/cmd_vel",
            CmdVelCallback
        );

        // Register a publisher for sensor data back to ROS
        ROSConnection.instance.RegisterPublisher<SensorMsgsImage>(
            "/unity/camera/image_raw"
        );
    }

    void CmdVelCallback(GeometryMsgsTwist msg)
    {
        // Apply velocity commands to the robot in Unity
        float linearSpeed = (float)msg.linear.x;
        float angularSpeed = (float)msg.angular.z;
        // Apply to rigidbody or articulation body controller
    }
}
```

### ROS-side endpoint node

```python
import rclpy
from rclpy.node import Node
from ros_tcp_endpoint.tcp_server import TcpServer


class UnityEndpoint(Node):

    rclpy.spin(node)
    rclpy.shutdown()
```

## Deep dive subtopics

### Physics engine comparison

The choice of physics engine significantly affects simulation fidelity and stability. Gazebo supports four engines, each with distinct characteristics.

#### ODE (Open Dynamics Engine)

ODE is the default physics engine in Gazebo. It uses constraint-based dynamics with a Dantzig or iterative solver for joint constraints.

| Property | Value |
|---|---|
| Solver | Dantzig (exact) or iterative (fast) |
| Contact model | Coulomb friction with split impulse |
| Strengths | Fast, well-tested, stable for moderate contact |
| Weaknesses | Simplified friction model, struggles with rolling contact |
| Best for | Wheeled robots, simple bipeds, manipulation tasks |

**Key parameters:**
- `cfm` (Constraint Force Mixing): Controls constraint softness. Higher values make joints spongier.
- `erp` (Error Reduction Rate): Controls how aggressively joint errors are corrected. Default 0.2.
- `contact_max_correcting_vel`: Maximum velocity correction at contact points.
- `contact_surface_layer`: Thin layer around collision geometry for early contact detection.

#### Bullet

Bullet provides more sophisticated collision detection and soft-body physics.

| Property | Value |
|---|---|
| Solver | Sequential impulse |
| Contact model | Split impulse with Coulomb friction |
| Strengths | Better friction modeling, soft body support, ragdoll dynamics |
| Weaknesses | Slower than ODE for large scenes, less mature ROS integration |
| Best for | Humanoid locomotion, deformable terrain, complex contact |

#### DART (Dynamic Animation and Robotics Toolkit)

DART uses an impulse-based approach and maintains a complete dynamics model of the kinematic tree.

| Property | Value |
|---|---|
| Solver | Impulse-based with constraint stabilization |
| Contact model | Rigid contact with LCP or PGS solver |
| Strengths | Accurate dynamics, Skeleton API, collision detection quality |
| Weaknesses | Slower initialization, smaller community |
| Best for | Biomechanical modeling, accurate humanoid dynamics research |

#### MuJoCo (Multi-Joint dynamics with Contact)

MuJoCo is optimized for control and reinforcement learning. It uses a smooth constraint model and is extremely fast for contact-rich simulations.

| Property | Value |
|---|---|
| Solver | Smooth contact with Newton solver |
| Contact model | Relaxed rigid contact with smooth approximation |
| Strengths | Fastest for contact-heavy tasks, excellent for RL, accurate friction |
| Weaknesses | Commercial license (free for research), limited rendering |
| Best for | Reinforcement learning, dexterous manipulation, humanoid locomotion research |

### Sensor simulation fidelity and noise models

Simulated sensors must include realistic noise to be useful. A perfect sensor produces algorithms that fail in the real world.

#### Gaussian noise model

Most sensor plugins support additive Gaussian noise:

```
measured_value = true_value + N(μ, σ²)
```

Typical noise parameters:

| Sensor | Parameter | Typical value | Units |
|---|---|---|---|
| IMU angular velocity | σ | 0.0017 | rad/s |
| IMU linear acceleration | σ | 0.0196 | m/s² |
| Camera pixel intensity | σ | 0.007 | normalized |
| LiDAR range | σ | 0.01 | m |
| Depth camera depth | σ | 0.005 | m |

#### Temporal noise sources

- **Jitter**: Variation in actual update rate vs nominal rate. A 30 Hz camera may actually publish at 28-32 Hz.
- **Latency**: Time between image capture and topic publication. Typically 10-50 ms depending on resolution and processing.
- **Dropped frames**: Occasional missing messages due to processing load.

#### Spatial noise sources

- **Distortion**: Lens distortion in real cameras (barrel, pincushion). Gazebo can simulate this with the `<distortion>` tag.
- **Resolution limits**: Pixel density affects minimum detectable object size.
- **Field-of-view roll-off**: Real lenses lose sharpness at edges.

#### Domain randomization techniques

Domain randomization varies simulation parameters across training episodes to make policies robust to reality gaps:

- **Visual randomization**: Randomize texture colors, lighting intensity, and shadow softness.
- **Physics randomization**: Vary friction coefficients (±20%), mass (±10%), joint damping (±30%).
- **Sensor randomization**: Vary noise levels, update rates, and latency.
- **Environmental randomization**: Randomize floor friction, obstacle positions, and lighting direction.

### Collision geometry vs visual geometry tradeoffs

Visual geometry defines what the robot looks like. Collision geometry defines how the physics engine computes contacts. They should almost always be different.

#### Why simplify collision geometry?

- **Performance**: Physics engines check contacts between every pair of collision shapes. Complex meshes with thousands of triangles dramatically slow contact detection.
- **Stability**: Concave meshes cause interpenetration and tunneling. Convex hulls and primitives (boxes, spheres, cylinders) are numerically stable.
- **Accuracy**: Mesh collisions can miss thin features. Primitives provide predictable, analytically computable contact points.

#### Common simplification strategies

| Original geometry | Collision approximation | Tradeoff |
|---|---|---|
| Mesh arm with fingers | Capsule for each finger, cylinder for arm | Loses finger-level precision, gains speed |
| Shoe with tread pattern | Flat box | Loses sole geometry, gains stability on ground contact |
| Head with facial features | Sphere | Loses facial collision, gains broad-phase efficiency |
| Table with curved legs | Box top + cylinder legs | Loses leg curvature, gains contact stability |

#### Convex decomposition

For concave meshes that need more fidelity, convex decomposition tools (V-HACD, CoACD) break a mesh into convex pieces:

```
# Using CoACD for convex decomposition
pip install coacd
python -c "
import coacd
mesh = coacd.Mesh('robot_hand.obj')
parts = coacd.coacd(
    mesh,
    max_convex_hull=16,
    preprocess_mode='auto',
    resolution=500
)
for i, part in enumerate(parts):
    part.export(f'collision_part_{i}.obj')
"
```

### World building best practices

#### Layout principles

1. **Start simple**: Begin with a flat floor and a few primitives. Add complexity only when the base scenario works.
2. **Use realistic dimensions**: Human doorways are 0.8 m wide. Standard table height is 0.75 m. Hallways are 1.2-1.8 m wide.
3. **Define clear boundaries**: Walls should extend beyond the camera frustum to prevent agents from seeing empty space.
4. **Texture for perception**: Use distinct textures for different surfaces so vision algorithms can distinguish them.

#### Physics world configuration

- **Time step**: 0.001 s (1 kHz) is standard for robotics. Slower time steps miss fast dynamics. Faster steps waste computation.
- **Solver iterations**: 50-100 iterations for ODE. More iterations improve contact stability but increase computation.
- **ERP/CFM tuning**: Increase ERP for stiffer joints. Increase CFM for more compliant (springy) behavior.
- **Contact parameters**: Adjust friction, bounce, and max correcting velocity per material pair for realism.

#### Common world objects

| Object | Purpose | Physics considerations |
|---|---|---|
| Tables | Manipulation tasks | Must support heavy objects, high friction surface |
| Chairs | Navigation obstacles | Complex geometry, use convex decomposition |
| Doors | Transition between rooms | Hinge joint with limits, trigger zones |
| Ramps | Incline locomotion testing | Smooth mesh, high friction to prevent sliding |
| Stairs | Vertical navigation challenge | Step height 0.15-0.20 m, tread depth 0.25-0.30 m |
| Narrow passages | Path planning constraints | Width 0.8-1.0 m for humanoid |
| Moving obstacles | Dynamic avoidance | Apply velocity commands, collision triggers |

### Performance optimization for large scenes

#### Level of detail (LOD)

Reduce visual geometry complexity for distant objects. Gazebo supports LOD through the `<lod>` element in SDF:

```xml
<link name="table_link">
  <visual name="high_detail">
    <geometry>
      <mesh uri="model://table_high.dae"/>
    </geometry>
    <lod>0 20</lod>
  </visual>
  <visual name="low_detail">
    <geometry>
      <mesh uri="model://table_low.dae"/>
    </geometry>
    <lod>20 100</lod>
  </visual>
</link>
```

#### Spatial partitioning

Gazebo uses octree-based spatial partitioning for broad-phase collision detection. Ensure static objects are marked `<static>true</static>` so the engine does not recompute their bounding boxes every frame.

#### Contact filtering

Limit which links can collide with each other using contact filters:

```xml
<contact>
  <collision name="left_foot_collision">
    <filter>
      <minus/>
      <group name="self_collide_group"/>
    </filter>
  </collision>
</contact>
```

#### Parallel simulation

Isaac Sim and NVIDIA's GPU physics engines support massive parallelization. For CPU-based Gazebo:

- Run multiple independent worlds on separate threads.
- Reduce sensor resolution for non-critical sensors.
- Use `<always_on>false</always_on>` for sensors not needed every frame.

#### Memory management

- Use primitive shapes (boxes, cylinders, spheres) instead of meshes when possible.
- Compress texture maps to 1024x1024 or smaller.
- Remove unused models from the world file.
- Avoid loading the entire model database; reference only needed models.

A humanoid assistant must carry a bottle from the table to the shelf. In simulation, define:

- Failure states: blocked path, low confidence object detection, unreachable shelf, unstable pose.

|---|---|---|
| 1 | Clear path, known object | Navigate, grasp, deliver |
| 2 | Narrow passage blocked by chair | Replan path, avoid collision |

## Sim-to-real transfer techniques

The reality gap between simulation and the physical world is the primary challenge in deploying sim-trained policies.

### System identification

System identification (SysID) measures real hardware properties and replicates them in simulation:

1. **Mass and inertia**: Weigh each link and compute inertia from geometry or CAD models.
2. **Friction coefficients**: Drag tests on real surfaces measure static and kinetic friction.
3. **Joint friction**: Apply known torques and measure joint displacement.
4. **Sensor calibration**: Run intrinsic calibration (camera intrinsics, IMU bias) and extrinsic calibration (sensor-to-robot transforms).

### Domain adaptation strategies

- **Teacher-student training**: Train in simulation with privileged information (ground-truth state), then distill into a student policy that uses only real-world observable inputs.
- **Sim-to-real fine-tuning**: Pre-train in simulation, then fine-tune on a small amount of real-world data.
- **Residual policy learning**: Use a sim-trained base policy and learn a residual correction from real data.

### Domain randomization checklist

| Parameter | Randomization range | Rationale |
|---|---|---|
| Ground friction | 0.5-1.2 | Floor materials vary widely |
| Joint damping | ±30% of nominal | Manufacturing tolerances |
| Motor strength | ±15% of nominal | Battery voltage and temperature effects |
| Sensor noise | ±50% of nominal | Environmental conditions affect noise |
| Object mass | ±20% of nominal | Real objects have unknown weight |
| Lighting intensity | 0.5-2.0x | Indoor/outdoor lighting variation |
| Camera color balance | ±30% per channel | Different cameras, white balance settings |
| Gravity | 9.78-9.83 m/s² | Altitude and latitude effects |

### Evaluation in simulation before real deployment

1. Run 100+ simulation episodes with full domain randomization.
2. Measure success rate, collision frequency, and task completion time.
3. Test worst-case scenarios (extreme noise, maximum friction variation).
4. Verify that no single randomization seed causes catastrophic failure.
5. Deploy to real hardware with a spotter and emergency stop ready.

## Common simulation pitfalls

### 1. Interpenetration and explosion

**Symptom**: Robot links pass through each other, then the physics engine applies massive correction forces causing the model to fly apart.

**Cause**: Time step too large, contact parameters misconfigured, or collision geometry is concave.

**Fix**: Reduce `max_step_size` to 0.0005 s, increase solver iterations, use convex collision geometry.

### 2. Floating-base instability

**Symptom**: Robot drifts or oscillates in free space without ground contact.

**Cause**: Missing ground plane, incorrect gravity direction, or URDF coordinate frame errors.

**Fix**: Verify ground plane is loaded, check `<gravity>` direction is negative Z, validate URDF origins.

### 3. Joint limit violations

**Symptom**: Robot joints bend beyond physical limits or oscillate at limits.

**Cause**: Joint limits not defined in URDF, or PID gains are too aggressive.

**Fix**: Add `<limit>` elements to all joints, tune PID controllers, add joint damping.

### 4. Sensor aliasing

**Symptom**: Perception algorithms work in simulation but fail in reality.

**Cause**: Simulated sensors update at perfect intervals with no jitter or dropped frames.

**Fix**: Add temporal noise to sensor update rates, simulate occasional frame drops, add latency.

### 5. Gravity and inertia mismatch

**Symptom**: Robot falls over immediately or moves sluggishly.

**Cause**: Inertia values are incorrect, or mass is unrealistic.

**Fix**: Use CAD software to compute accurate inertia tensors, or use measured values from hardware.

### 6. URDF coordinate frame errors

**Symptom**: Robot parts appear in wrong locations or TF tree is broken.

**Cause**: Incorrect `<origin>` values in joints or links.

**Fix**: Visualize the URDF in RViz first, verify each joint origin against the robot's kinematic specification.

### 7. Model loading failures

**Symptom**: Gazebo reports "model not found" or crashes on startup.

**Cause**: Model paths are incorrect, meshes are missing, or Gazebo model database is not configured.

**Fix**: Use absolute paths, ensure all mesh files exist, set `GAZEBO_MODEL_PATH` environment variable.

## Glossary

| Term | Definition |
|---|---|
| **URDF** | Unified Robot Description Format. An XML format defining robot kinematics, dynamics, and visual/collision geometry as a tree of links and joints. |
| **SDF** | Simulation Description Format. An XML format used by Gazebo to describe complete simulation worlds including physics, lighting, and models. |
| **Digital twin** | A simulated representation of a physical system used for testing, training, and monitoring before or alongside real-world deployment. |
| **Domain randomization** | Varying simulation parameters (friction, lighting, noise, mass) across episodes to make learned policies robust to the sim-to-real gap. |
| **Sim-to-real gap** | The difference between simulated and real-world behavior caused by unmodeled physics, sensor noise, and environmental variability. |
| **ODE** | Open Dynamics Engine. A C++ library for simulating rigid body dynamics, the default physics engine in Gazebo. |
| **DART** | Dynamic Animation and Robotics Toolkit. A dynamics library focused on accurate simulation of articulated rigid body systems. |
| **MuJoCo** | Multi-Joint dynamics with Contact. A physics engine optimized for control and reinforcement learning with fast contact simulation. |
| **IMU** | Inertial Measurement Unit. A sensor combining accelerometers and gyroscopes to measure linear acceleration and angular velocity. |
| **LiDAR** | Light Detection and Ranging. A sensor that measures distances to surrounding objects using laser pulses, producing 3D point clouds. |
| **TF tree** | Transform tree. A hierarchical representation of coordinate frame relationships published by the robot_state_publisher. |
| **Convex decomposition** | Breaking a concave mesh into multiple convex pieces for use as collision geometry. |
| **System identification** | The process of measuring real hardware properties (mass, friction, damping) and replicating them in simulation. |
| **ROS TCP Connector** | A network bridge that streams ROS 2 topics between Unity and a ROS 2 workspace over TCP sockets. |
